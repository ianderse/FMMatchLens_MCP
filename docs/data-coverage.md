# Data coverage: Slice 0 audit

Source: two real recordings (FM27 on the user's Windows PC, FMMatchLens v0.7.0, archive format 2.8). Sections 1 to 14 describe the first,
`2026-08-31-Farnham-vs-Torquay-0-3.fmlens`, SHA-256 `72d302061a1a3ec92aaf9dd0d2e99adb4d79bf6b3f6077845299665f2cc76294`, 1,831,146 bytes.
Section 15 adds the second, `2026-09-05-Hemel Hempstead-vs-Farnham-1-2.fmlens`, SHA-256
`f87efd453bf68705b05bec77d5d6452ef2396c4a5995de126ea85cc7f6c9608c`, 1,913,775 bytes, and says which statements above it confirms or
contradicts. The filename scores ("0-3", "1-2") are claims; the data confirms them only as the last observed score (see Completion).

Reproduce: `node scripts/audit/audit.mts tests/fixtures/local/2026-08-31-Farnham-vs-Torquay-0-3.fmlens audit-output` (the second recording: the same command with its path and a different output directory)
(full JSON in `audit-output/audit.json`, gitignored; a name-free numeric summary is committed at
`tests/fixtures/farnham-torquay-0-3.summary.json`). Labels used below: **measured** = computed from the file; **inferred** =
a reading that fits the numbers but has no independent confirmation; **upstream code** = from the vendored v0.7.0 sources;
**unresolved** = cannot be decided from this data.

## 3. Integrity, completion, time

**Integrity (measured).** Records: 2 metadata (first one empty, 0 players, captured tick -1), 10 metadata deltas, 1 rating-model
record, 19 chunks, 1 final index, 1 end record. 15,768 frames, 12 metadata revisions. Chunks hold 1 to 2,308 frames; 3,756,226
bytes uncompressed, 1,801,393 compressed. Final-index frame count, first/last tick (3 / 21351) and score (0-3) equal the decoded
frames. File integrity = `valid`. The audit relies on the upstream parser for CRC checks; the record walk in `audit.mts` is an
independent structural check, not a second CRC implementation.

**Completion (measured, then unresolved).**
- The end record carries only a wall-clock timestamp. Upstream code: `MarkEnded` runs when the plugin sees the game match object
  terminate (epoch reset, cleared runtime teams or the terminal probe). That is a match-object lifecycle signal, not a rule
  result. A user leaving or skipping may produce the same signal (upstream code, not tested).
- The last frame is at tick 21351, display tick 21028 = **87.6 game minutes**, period 2, ball in play: the last event is at tick
  21346 and 4 events fall within the last 10 ticks, possession belonged to the away side. No stoppage-time or whistle marker.
  A natural full time cannot occur before 90:00. Last goal at 84.2 min, 3.45 game minutes before the last frame.
- The rating model's `matchPhase` is 6 for all period-1 frames and 7 for all period-2 frames and never changes again; no
  distinct final phase was observed (meaning of the values is unverified).
- Last frame captured 27.6 s of wall time before the end record. The live API reported `status: "ended"`, `inMatch: false`.
- Verdict: closed and `valid`, but no source signal of full time. **Completion = `unknown`; 0-3 is observed, not final.**
  Whether FM's final score was also 0-3 and what happened after minute 87.6 (skip to end, exit) needs the user.
- **User-reported (not verifiable from the file):** the recording stops at minute 87.6 because the user skipped the rest of the match.
  The match therefore very likely reached full time, but the recording did not, and any goal after 87.6 is unseen. The verdict above
  stands: observed 0-3, completion `unknown` until `fmmi match confirm`. Confirming attests that the *match* reached full time; it does
  not change capture coverage, which stays `partial` with `end_capture_ends_at` = period 2, tick 21351 (game minute 87.62). A confirmed
  score that differs from the observed one needs `--allow-score-change` and is stored as a manual final score; observed counters are
  never altered.

- Tick gap at halftime: 83 ticks. No events fall in it.
- `displayTick` does **not** reset to zero. It restarts at 45:00 (10,800) in period 2, so values 10,801-11,040 occur in both
  periods. A display minute is ambiguous without the period. The spec's `(period, tick, sequence)` boundary is required.
- 240 ticks = 1 game minute. Evidence: upstream uses `/240` everywhere; 16 of 18 substitution minute labels equal
  `floor(displayTick/240)+1` (the other two are the halftime change, labelled 45); period-1 stoppage is exactly 240 display ticks.
  Elapsed playing minutes = sum of tick deltas inside one period while `isOnPitch`, divided by 240 (inferred rate, strong).
  Outfield starters play 88.60 min (45.99 + 42.61).
- Ticks are not contiguous: 15,029 of 15,767 deltas equal 1; 738 gaps; 5,581 missing ticks (live API says 5,583, which
  counts ticks 1 and 2 before the first frame); largest gap 127 ticks (about 32 game seconds). Nothing decreases or repeats.
  Gaps are spread through the match (not clustered). Cumulative counters can therefore only be sampled, never assumed per tick.
- `sequence` is strictly increasing across frames, starts at 186,000, advances 1 to more than 10 per frame, and is not tied to
  tick. It is a capture counter, useful only as a tie-breaker. Event identity is the separate event `sequenceIndex`.
- Wall-clock timestamps: 9,637 of 15,767 deltas are zero; not usable for ordering.

- Substitution minute labels (`subbedOnMinute`/`subbedOffMinute`) are 1-minute resolution; the exact tick is the `isOnPitch` flip.
  Same-tick batches: home 4 players at tick 15,062 (two off, two on), away 4 players at tick 15,800. The off/on pairing is not in

## 4. Identity

- 36 metadata players (18 per side: 11 starters, 7 bench), slots 0-17 home, 18-35 away. 31 played; 5 unused bench players never
  appear on the pitch.
- `uid` present for 36/36; `playerId == uid` for 36/36; no negatives, no duplicates. Upstream code: `playerId` is the player's
  database UID read from the game's person object when available, otherwise a negative fallback `-(slot+1)`. uid magnitudes: 22
  below 1e8 and 14 at or above 2e9 (the latter probably generated/regen records, inferred).
- `slot` is a match-local index in frame and metadata records, stable for the whole file (0 mismatches against metadata over
  15,768 frames). Not an identity across matches.
- **Trap (measured): event `playerSlot` and `receiverPlayerSlot` are side-local (0-17 for each side)**, not the global frame slot.
  Away slot 10 in an event is global slot 28. Use `playerId` for joins, or add the away base (18).
- Persistence of `uid` across matches: **observed for 17 players across two recordings** (section 15); across saves and transfers
  **unresolved**. Names remain presentation only; a uid is trusted as a repeat only together with the same name.
- Source match ID: generated by the plugin from the recording start time (`match-` + Unix ms, equality measured). It identifies a
  recording, not an FM fixture. A replay or re-simulation of the same fixture would get a different ID (not tested); the same ID
  with different bytes has not been seen.
- Human-managed side is identifiable from `manager.isHumanControlled` (home here). Farnham was **home**.

## 7. Coordinates, axes, direction (measured)

- Units are metres, origin at pitch centre. Pitch half-width 34.3125 m, half-length 50.325 m (pitch about 68.6 x 100.7 m, from metadata).
- Event `lateralPosition` corresponds to player `x` (width axis); event `longitudinalPosition` corresponds to player `y` (length axis).
  Test: median distance between a completed pass's trajectory end and its receiver's position at completion is 0.004 m under that
  mapping, versus 27 to 56 m under the three alternatives.
- Observed ranges: event lateral -34.57..34.56, longitudinal -53.12..52.81; on-pitch-flagged players x -40.3..36.08, y -57.25..57.25.
  Values beyond the touchlines and goal lines occur (throw-ins, corners, goal kicks), so do not clamp silently.
- Direction: home attacks toward -y in period 1 (goalkeeper mean y +46.1) and +y in period 2 (-45.7); away reverses
  (-43.2 then +43.3). The event flag **`0x100` set means that event's team attacks toward +y**: unset/set per team-period is
  100% consistent over all passes (home p1 292/292 unset, p2 317/317 set; away p1 322/322 set, p2 227/227 unset) and over shots and
  goals. Per-period normalisation is therefore derivable by two independent signals.
- Upstream display code (upstream code, `passMap.ts`): node X is built from `event.y` (the lateral value, as a 0-100 percentage),
  node Y from `100 - event.x`. Units are percent of pitch, not the spec's `[0,1]`. Our normalisation must start from the metre values.
- Normalised `[0,1]` attack-direction coordinates and the 2/3 final-third threshold (spec 7.7) are computable from these facts;
  not yet implemented.

**Flags (measured bit counts across all 1,892 events).** `0x1` on 1,585 (appears to be a base bit); `0x100` direction (section 7);
`0x2` key pass (16; per-player key-pass counters agree exactly with the flag, 0 of 36 differ); `0x40` on crosses equals the corners
counter exactly (3 and 6); `0x8` on passes equals the player throw-in counter exactly for all 36 players (15 and 9). So `0x8` = throw-in

them; unverified here). `0x4`, `0x400`: unknown.

**Pass scope and reconciliation (measured).** Team counter `passes` and `passesCompleted` equal the count of pass events

**Recipient gate (spec 7.2):**
1. Verified receiver semantics: *internally corroborated* (all four checks above); not checked against the FM UI or upstream dashboard.
2. Coverage >= 95%: **pass** (100%).
3. Reconciliation within tolerance: **pass** (0 residual under the documented scope).

## 9. Ground-pass classification

No ground/air flag exists in the event schema (fields are `eventType`, `flags`, `trajectoryPoints` with lateral/longitudinal only).
Frames carry ball height (`ballZCentimeters`, 0 to 1,941 cm). The maximum ball height during the flight of the 1,013 completed passes
has median 6 cm, p90 209 cm, p99 616 cm. That suggests ground and air passes are separable, but there is no ground truth and
frames are sampled (2 to 8 per pass), so no rule is validated. **Unavailable; ground service stays null** (spec 7.7). A later spike
may propose a threshold rule and validate it against the FM UI.

## 12. Not verified (cannot be established from this one offline recording)

1. **Scenario set.** Covered now: a home match with substitutions (Torquay) and an away match with substitutions that reached 94.03 display
   minutes (Hemel; section 15). Not covered: a match quit midway on purpose, extra time or a shootout, red cards or injury substitutions,
   penalties in a shootout, an instant-result match (whether it is recorded at all), a replay of the same fixture (source-match-ID
   behaviour), a recording interrupted by a crash (`recovered_prefix`), a second save or a transferred player (uid persistence beyond the
   two recordings here).
2. **Comparison to the FM27 UI.** Score, xG, shots, passes, a few player stats, substitution minutes and the final score after minute 87.6
   have not been compared with FM27. Needs the user. In particular: what FM showed as final score, whether the match reached full time,
   and what the user did at 87:37 (skip, exit, leave).
3. **Upstream dashboard check.** "1 match archive can be opened in upstream dashboard" has not been tried.
4. **Live API.** Only `/api/health`, `/api/archives` and `/api/match/status` were captured. `/api/match/current`, `/meta`, `/frames`,
   `/formation/history`, `/momentum/*` and the WebSocket were not observed; live-versus-archive agreement for frames is unchecked.

## 16. Chance creation by wing across matches (dictionary 1.2)

`chance_creation_by_wing_trend` (v2) pools, for the managed team and its opposition, shots, per-shot xG, crosses, completed crosses,
final-third entries and danger-area entries per attack lane, as summed counts with a per-90 rate over the measured minutes of the
contributing matches. The lane logic and definitions are the per-match ones (`attack_lane`, `opposition_*_by_lane`,
`danger_area_entries_by_lane`); no lane is ranked. On the two real recordings the lane totals plus unlocated shots equal the shot counters
of both recordings (Farnham 6 + 13, opposition 12 + 8), because every shot event carries a location. xG per lane is the sum of per-shot xG
attributed from counter steps; shots whose xG could not be attributed are disclosed, never spread over lanes.

## 18. Live path in a real match (2026-10-31): what was seen, and the `held` state

Seen once, during one real match, on 2026-10-31 (one session; nothing here is a guarantee for other match states):
- All nine HTTP routes answered. The WebSocket delivered `connection_status` and `realtime_tick` envelopes. `formation_changed` was not seen.
- `/api/match/meta` failed the first schema because the 14 of 36 players who were substitutes carry `inPossession: null` and `outOfPossession: null`
  (they hold no tactical assignment until they come on). The reader reported `metadata_invalid`. The schemas (`MetadataSchema`, `FormationEntry`)
  now accept null; the reader then reached `fresh` on the real match. How a substitute's assignment appears when he comes on mid-match was not
  observed; the fake plugin models it as a formation entry that replaces the null.
- `fmmi live check` had reported `meta` ok on a capture whose full response failed, because it validated a sanitised skeleton (arrays cut to two
  elements). The verdict is now taken on the raw response at capture time (section 17 and `docs/setup-windows.md` section 9).
- **Half-time gives no break signal.** At the real half-time `/api/health` said status `live`, `inMatch: true`, tick 11093; `/api/match/status` said status
  `live`, period 1, `lastTick` 11093; `/api/match/current` held tick 11093, display tick 11092, period 1, with `capturedUnixMilliseconds` aging while the
  sequence did not change; the socket stayed open. Before the fix the reader called this `stale` (`latest_frame_too_old`) after 10 s and every analysis
  tool refused, which made a halftime briefing impossible. The state `held` now covers it: plugin reachable, `inMatch` true, same match, the reader's
  accepted tick equals the plugin's `lastTick` (lag 0), and the newest frame older than the freshness limit. It does not rely on the socket. It says
  how long no frame arrived and that the game is not advancing for a reason the source does not give (pause, break or finished); `likelyBreak` is a
  labelled guess from the game clock. The specification lists fresh / stale / not-in-match only: `held` is a deviation, recorded here.
- A call after a gap returned `stale` with `catchingUp: true`, 4,400 ticks behind; a live call now waits up to about 8 s for catch-up.
  Catch-up from zero was measured on the fake plugin with a full-match frame count in virtual time (the 4 requests/s governor is the limit):
  23,046 frames took 37 requests and 9 s, in one call. A real match of about 16,400 frames needs roughly 21 history pages plus about 6 other
  requests, about 7 s. The first call after starting the server mid-match can therefore reach the 8 s budget and answer `stale` with
  `catchingUp: true`; the next call finishes. Later calls read only the new frames.

Game minutes. A minute is never tick / 240: in period 2 the display ticks restart at 45:00 and the tick to display-tick offset is 564 in the Hemel

use the first and last display tick of each period and report the minute as unknown when the offset differs between them.

Identity. Match-scoped results (`get_match_summary` roster, `get_player_match`, `get_striker_service` subject and comparator, report and compare players)
state `identity` (`persistent`, `linked` or `match_local`) and `persistentPlayerId` (`pe_...` or null). It is read from the catalog on every call and is
not part of any cached value.
