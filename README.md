# FMMatchLens_MCP

Local-first match intelligence for Football Manager 27. It imports `.fmlens` recordings made by the [FMMatchLens](https://github.com/osnsyc/FMMatchLens) v0.7.0 BepInEx plugin (format 2.8) into a local catalog, computes tactical evidence with deterministic code, and serves it through the `fmmi` CLI and a read-only MCP server, so an LLM client can review a match using sourced numbers instead of guesses.

No game, network or LLM is needed to import or analyse recordings, and no LLM runs inside this project. Football Manager is only needed to make recordings and for the optional live tools.

## Quick start

Windows, Node >= 22.18.

    npm install
    npm link
    fmmi setup

Then play, and ask Claude about the match. Setup finds your recordings folder, creates your save, imports what is there and registers the MCP server with Claude Code, so a new Claude Code session can read your matches and picks up new recordings by itself. Nothing is needed after a normal match.

Windows is the tested platform (Windows 11, PowerShell, Claude Code). macOS and Linux are untested: the code avoids Windows-only calls where it can, but the Steam folder search, the `claude` launcher handling and every instruction here have only been exercised on Windows.

`fmmi` on its own shows where you stand (your save, how many matches, what is new, the next step). `fmmi --help` lists every command. If you use no MCP client, or want to correct a final score, `fmmi sync` imports new recordings and asks about the ones that need a confirmation.

## What is and is not verified

Verified on real data:

- Parsing, statistics and counter reconciliation on two real recordings (Farnham 0-3 Torquay, Hemel Hempstead 1-2 Farnham). A third (Folkestone 2-1 Farnham) imported as a full, valid recording.
- Receptions recounted independently from raw events, and attacking-lane orientation checked against where labelled players actually stand.
- Cross-match player trends, and continuation of a truncated copy of a real recording.
- The Hemel role timeline, confirmed by the user from their own game.
- Claude Code reaching the tools and answering a plain review question in the five-part structure, from any folder.
- `npm link` and `fmmi setup` on one real Windows machine: the Steam folder search, reusing an existing save, real registration with Claude Code, and a second run changing nothing.
- Automatic import through the real server, using copies of real recordings. The game folder was unchanged.
- On one real match, in play: all nine HTTP routes answered, full responses passed the schemas, the socket delivered ticks, and all three live tools returned `fresh` data.

Not verified:

| Area | State |
| --- | --- |
| Live `held` state | Built from what the plugin reported at a real halftime, but tested only against a fake plugin; no real briefing at a break yet |
| Live figures | Never compared with FM's match stats or a finished recording |
| Automatic import after a real match | Tested with copied files in place of a match finishing in the game; a CLI import at the same moment was tested only on synthetic recordings |
| The interactive setup prompts | Real runs used `--yes`; the prompts have only run against a scripted terminal |
| WebSocket `formation_changed` | Never seen from a real plugin |
| Remote MCP | Run on loopback only; no Tailscale, no real network, no Mac, no OMP |
| LLM use | Claude Code only; the review checker has only seen test answers |
| Pass receivers | Internally corroborated, not checked against the FM match screen |
| Player `uid` | Not checked across different saves or transfers |
| In-progress recordings | Whether the plugin keeps earlier frames byte-identical while writing is unknown |

Known limits:

- **Full time is inferred.** The source has no full-time signal. `full_match` is a heuristic (clean close, zero baseline, no gap over 240 ticks, last frame at or after 90:00). A full-match capture counts in season figures without a confirmation, but its completion stays `unknown` and its score is labelled `observed`, not final. A partial recording is excluded until you confirm it with `fmmi sync` (or `fmmi match confirm`), and a manual confirmation always takes precedence and can correct the score.
- **Some data does not exist in recordings.** There is no ground/air pass field, so ground service is reported as unavailable, never inferred. Progressive passes come from counters only. Fouls and clearances do not reconcile and are not used as verified.
- **Comparisons are observational.** Findings carry context flags such as score state, but they are not adjusted for it, and opposition strength is unavailable.
- **MCP responses are about twice their JSON size** on the wire, because each carries both text and structured content.
- **The remote token comes from an environment variable.** The OS credential store is not implemented.

## Setup

Windows, Node >= 22.18 (developed on Node 25.1). Node runs the TypeScript directly; there is no build step.

    npm install
    npm link          # puts `fmmi` and `fmmi-mcp` on your PATH
    fmmi setup

`fmmi setup` is guided and safe to run again. It looks for the plugin's recordings folder (the standard Steam paths, then the libraries listed in Steam's `libraryfolders.vdf`), shows what it found and asks; if it finds nothing it asks you to paste the path (quotes and line breaks from pasting are cleaned up). It remembers the folder and a default save in `config.json` under the catalog home, reuses your existing save (or names a new one after the club you manage), imports every finished recording, sets your club, asks for the final score of any partial recording, and offers to register the MCP server with Claude Code at user scope (all projects). It writes only under the catalog home, plus Claude's own settings through the `claude` command and only after you agree. For scripts: `fmmi setup --yes --archive-dir "<folder>" --save-name "<name>" [--no-mcp]`.

Without `npm link`, every command also works as `npm run fmmi -- <args>`.

    npm run typecheck && npm run lint && npm test

Real recordings for local tests go in `tests/fixtures/local/`. That folder is gitignored and recordings are never committed; the tests that need them skip when they are absent.

Data lives under `FMMI_HOME` (default `%LOCALAPPDATA%\fmmi`): `catalog.sqlite`, read-only content-addressed `snapshots/` and `config.json` (`archiveDir`, `defaultSaveId`). Flags win over the environment (`FMMI_ARCHIVE_DIR`, `FMMI_DEFAULT_SAVE`), which wins over `config.json`. Source recordings and the game folder are never modified. After upgrading, run any `fmmi` command once so the catalog migrates before the MCP server opens it (the server never migrates).

## Use the CLI

    fmmi                              # home screen: save, matches, what is new, the next step
    fmmi setup                        # once
    fmmi sync                         # optional: import new recordings now, confirm partial ones [--include-in-progress] [--all]
    fmmi report                       # the latest match
    fmmi doctor

`--save` is optional everywhere: the default save, else the only save (it takes a save name or id). A match reference may be `latest`, an exact id or a team-name fragment (`fmmi report hemel`); a player reference may be a `p_` id, a `pe_` id or a name fragment (`fmmi player latest alexander`). An ambiguous reference lists the candidates and stops. `--team` defaults to your club wherever a command needs one.

`fmmi sync` imports new recordings from the configured folder, skips the file the plugin is still writing (`match-<digits>.fmlens`, renamed when the match ends; `--include-in-progress` imports it as a partial) and asks about the recordings that need a confirmation: Enter confirms the observed score, a typed score stores that score (you are asked again when it differs), `n` skips. Without a terminal it never asks; it lists the exact `fmmi match confirm` commands instead. `--json` never prompts.

    fmmi ingest path\to\match.fmlens            # file or directory
    fmmi ingest --new                           # configured folder, including a recording still in progress
    fmmi list [--all-saves] [--team <ref>] [--season 2026-27] [--limit n] [--cursor c]
    fmmi show hemel
    fmmi match confirm latest --score 0-3 [--allow-score-change]
    fmmi match move <match> --save <destination save>
    fmmi recording resolve <recordingRevisionId> --as separate-occurrence|ignored|continuation|alternate

Single-match analysis. These accept `--json`, `--recording-revision <id>`, windows (`--from <period>:<tick> --to <period>:<tick>` or `--from-minute/--to-minute [--period]`) and `--scope counter_scope|open_play|all_passes`:

    fmmi report [match] [--format markdown]     # facts, deterministic findings, evidence quality
    fmmi summary <match> [--team <ref>]         # compact summary with the complete recorded roster
    fmmi player <match> <player>
    fmmi network <match> [--team <ref>] [--min-passes n] [--limit n]
    fmmi service <match> <player> [--compare <player>]
    fmmi threat <match> [--team <ref>]          # how the opponent of the team created chances, by attacking lane
    fmmi compare <match> [--team <ref>] [--players a,b] --a-from-minute 1 --a-to-minute 45 --a-period 1 --b-from-minute 46 --b-period 2
    fmmi status [match]                         # recording evidence status, or catalog health

Season history and notes. `--team` takes a team id, a club alias or an exact team name in the save, and defaults to the save's managed team:

    fmmi trends [--team <ref>] [--last n] [--home-away home|away] [--metrics a,b] [--season 2026-27] [--include-partial]
    fmmi review --last 5                        # rolling review with exact contributing matches and pooled rates
    fmmi players [--name text] [--team <ref>]
    fmmi player-trends --players pe_a,pe_b [--last n]   # 1-4 persistent players
    fmmi player link <id> <id>...               # join match-local ids and at most one persistent id; audited
    fmmi player unlink <p_id>
    fmmi note add <match> --minute 60 [--period 2] [--team <ref>] --setting Mentality --prior-value Balanced --new-value Positive [--text note]
    fmmi note list [--match <match>]
    fmmi note supersede <noteId> [--minute m] [--new-value v] ...     # a correction is a new note; notes are never edited
    fmmi note compare <noteId> [--before 3] [--after 3]
    fmmi save team detect [--apply] | set --team <ref> | clear
    fmmi club alias add|remove|list --team <ref> --alias STFC
    fmmi aggregates rebuild

Add `--json` for machine output (schemas in `schemas/`, regenerated with `npm run schemas`). Set `FMMI_DEBUG=1` to write the stack of an `internal_error` to stderr; clients still see only the opaque error.

## Use the MCP server

`fmmi setup` registers it with Claude Code. To do it by hand, `claude mcp add` is easy to get wrong in PowerShell (it swallows `--`), so add this to your MCP configuration instead; `fmmi setup` prints the same block with your real paths when it cannot find `claude`:

    {
      "mcpServers": {
        "fmmi": { "command": "C:\\path\\to\\node.exe", "args": ["C:\\path\\to\\FMMatchLens_MCP\\packages\\mcp\\bin\\fmmi-mcp.mjs", "--live"] }
      }
    }

Other ways to start it: `fmmi-mcp` (after `npm link`), `npm run --silent fmmi-mcp`, `node scripts/review-check.mts --response review.md --results tool-results.json` to check a saved five-part review.

The server's tools are read-only and accept no file paths; it has thirteen tools by default and `saveId` is optional on all of them (the default save). `get_player_match` and `get_striker_service` accept a persistent `pe_` id as well as a match-local `p_` id.

**One deliberate exception to read-only.** The stdio server imports new finished recordings from the folder `fmmi setup` configured, into the configured default save, before it serves a catalog-reading call (at most once every 30 seconds, and once at startup). No tool argument can change the folder, a path or the save. It skips the in-progress `match-<digits>.fmlens` file, uses a short-lived separate writer (a busy catalog skips that round and retries later), never fails or blocks a call (it logs a category to stderr and adds a warning to the result), and reports what it imported as `newlyImported` on `list_matches` and `get_recording_status`. Turn it off with `--no-auto-import`; `--http` never imports. This departs from spec section 8.

The server's instructions ask clients to answer review questions in five parts: facts, interpretation, alternative explanations, action and confidence. A client can ignore those instructions, so there is also a `match_review` prompt that requests the structure directly (`/mcp__fmmi__match_review` in Claude Code). Client configuration is in `docs/setup-windows.md`.

## Optional: live match use

**Seen working on one real match in play; briefings at a break are not yet proven.** Live tools stay off unless you start the server with `--live`, which adds `get_live_match`, `get_live_player_analysis` and `get_recent_tactical_events`.

    fmmi live status                 # is the plugin reachable, is a match running
    fmmi live capture                # run DURING a real match, ideally once per half
    fmmi live check                  # validate that capture against this project's schemas
    fmmi note add --live --setting Mentality --prior-value Balanced --new-value Positive
    fmmi note compare <live note id, starts with ln_>

The reader talks only to `127.0.0.1:16726`, and no setting changes that address. It does nothing until a live tool is called, sends the plugin at most 4 requests per second, and keeps no frames. Every result names its snapshot (`live as of game minute N / period P / tick T`) and its state. `fresh` and `held` are analysed: `held` means the data is caught up but the game has stopped advancing, as at a pause, halftime or full time. The plugin does not say which, so any such label is a guess. A live note becomes a normal tactical note when the finished recording is imported.

## Optional: remote MCP

**Run on loopback only so far.** The HTTP transport is off unless you pass `--http`, and it serves the same read-only tools at `POST /mcp`.

    fmmi-mcp --print-new-token
    set FMMI_MCP_TOKEN=the-token-printed-above
    fmmi-mcp --http [--live] [--port 8787]

A bearer token is required on every request, including on loopback. The server speaks plain HTTP and binds `127.0.0.1` by default. A non-loopback bind needs a specific IP address plus `--allow-non-loopback`, `--allow-host` and `--private-transport tailscale|wireguard|tls-proxy|ssh-tunnel`; wildcard addresses are refused. Never expose it to a LAN or the internet, and never rebind the FMMatchLens plugin itself. Details are in `docs/setup-windows.md` section 10.

## How the evidence works

- **Status has three separate dimensions:** file integrity, capture coverage and match completion. A clean close is file integrity only, and confirming a match never changes capture coverage.
- **Reports hold facts and deterministic findings.** They contain no hypotheses or recommendations. Those belong to the LLM, which must cite the evidence.
- **Pass scope defaults to `counter_scope`** (all passes except throw-ins, crosses separate), the only scope that reconciles exactly to the cumulative counters.
- **Partial recordings are labelled partial**, with totals over the captured interval only.
- **Windows are half-open** and counters are read as a difference between boundaries; snapshots are never summed or interpolated, and a missing baseline gives `null` with a reason.
- **Lanes are from the attacking team's perspective**, so the opposition's left lane runs down the selected team's right flank. Threat is reported as per-lane counts, never a score, and no goal is attributed to a defender.
- **Ratings:** the in-game rating is observed. The breakdown is an upstream estimate with its residual and limits, and the game is never stated to use a weight.
- **Which matches count in season figures:** nonconflicting matches with a full-match capture, whether or not you confirmed them (an unconfirmed one is disclosed as `full_capture_unconfirmed`, its score is labelled `observed`, not final, and its completion stays `unknown`). Partial recordings wait for a confirmation. Confirmed matches that end early with a trustworthy baseline and at least 80 captured minutes count in rates only, disclosed as `early_ending`. A manual confirmation takes precedence.
- **Rates are pooled:** sum of numerators over sum of denominators, never an average of match ratios. Each row lists its contributing matches and exclusions.
- **Player identity is conservative.** A persistent `pe_` id needs the same positive uid in two or more matches of a save and the same display name. Otherwise the player stays match-local (`p_`) until `fmmi player link`. A name alone never merges players.
- **Tactical notes are manual and immutable**, and they are shown apart from changes the plugin observed. `compare_tactical_change` shows context and confounders and never states a cause.
- **Recordings are immutable revisions.** A recording that extends a known one with every earlier frame unchanged becomes a continuation automatically. Any difference in the earlier frames stays `identity_conflict` until `fmmi recording resolve`.
- **Cached aggregates are rebuilt, never served stale.** They are keyed by the dictionary and definition versions.
